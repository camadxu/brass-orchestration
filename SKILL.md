# Оркестровка для медных духовых

Сдавать партитуру можно только после прогона валидатора. Сборка без отчёта валидатора —
не сданная работа, а черновик: ручной воусинг даже простых 8 тактов дал 15 ошибок и 12
предупреждений, тот же материал после генератора и цикла правок — 0 и 0.

  ```bash
  "/c/Program Files/MuseScore 4/bin/MuseScore4.exe" -o out.pdf  in.musicxml   # PDF
  "/c/Program Files/MuseScore 4/bin/MuseScore4.exe" -o out.png  in.musicxml   # PNG постранично: out-1.png, out-2.png…
  "/c/Program Files/MuseScore 4/bin/MuseScore4.exe" -o out.mid  in.musicxml   # MIDI
  ```

## Инструменты скилла (`scripts/`)

| Скрипт | Что делает |
|---|---|
| `validate_brass.py` | Механическая проверка MusicXML: диапазоны, выносливость, дыхание, разрывы фактуры, параллельные квинты/октавы, ключи транспонирующих партий. `--level amateur\|pro`, `--json`, rc=1 при жёстких ошибках |
| `voice_quintet.py` | Генератор воусинга квинтета beam-search'ем по правилам валидатора: `--prog 'Bb,Eb,F,Bb' --bars 2 --rests 3,6 --out score.musicxml` |
| `make_parts.py` | Партии из партитуры (по файлу на партию, префикс-индекс в имени): `--out parts --pdf` |
| `split_part.py` | Одна партия в отдельный файл для быстрого рендера |
| `compare_scores.py` | Сверка аранжировки с исходником (метрики — читать `references/source-comparison.md` до интерпретации!) |
| `check_delivery.py` | Приёмка пакета: пересчёт нот, парность партий, lineage-диф |
| `imslp_fetch.py` | Скачивание public domain с IMSLP в обход JS-заглушки (имя объекта обязано содержать `IMSLP<id>-`) |

Python здесь и далее = полный путь из раздела «Окружение».

## Workflow A: аранжировка с нуля

1. **Источник**: MIDI/MusicXML/PDF/аккордовая сетка. Аудио — только референс; не транскрибировать
   аранжировку на слух и не заявлять точность.
2. **План до нот**: состав, уровень (любитель/про), тональности, форма с номерами тактов,
   кто ведёт мелодию/пэд/бас в каждой секции, бюджет дыхания. План показать до гравировки.
3. **Черновик**: аккордовый материал — через `voice_quintet.py`, не вручную (ручной отбор
   голосов регулярно ломает интервалику и параллельность — это то, что валидатор ловит).
   Free-form — MusicXML одним файлом, партии только генерацией из партитуры.
4. **Цикл генератор → валидатор**: `validate_brass.py score.musicxml --level amateur`.
   Исправить каждую жёсткую ошибку, обосновать каждое предупреждение. Повторять до
   «mechanically clean» — цикл и есть работа, первый черновик — нет.
5. **Рендер и партии**: MuseScore 4 (команды выше) + `make_parts.py`. Затем **смотреть рендер**:
   PNG-экспорт, читать каждую парту — ключи, знаки (Bb-партии в C при Bb-мажоре, валторна
   на бемоль меньше), паузы, добавочные линейки тубы. Сгенерированный файл — не гарантирия
   правильной печати.
6. **Партии**: `make_parts.py score.musicxml --out parts --pdf`. Без `--pdf` — только MusicXML.
   Партии без кия/многотактовых пауз игроки возвращают.
7. **Отчёт** — см. раздел «Отчёт» ниже.

## Workflow B: проверка готовой аранжировки против источника

Когда просят «проверь мою аранжировку по партитуре», а не «сделай аранжировку»:

1. Мастер MusicXML из пакета (не PDF). Вопрос «тот ли это файл» решается `sha256sum`, не mtime.
2. `.mxl` — это zip: распаковать, сравнивать `score.musicxml`. Партии могут быть с локализованными
   именами, мастер — с английскими: сопоставлять по порядку, не по имени.
3. `compare_scores.py` + `validate_brass.py`. Метрики сравнения читать только после
   `references/source-comparison.md` — половина цифр выглядит тревожно на здоровой транскрипции.
4. «Ошибка» — только когда два независимых источника согласны против аранжировки; остальное —
   кандидат + недостающее доказательство.
5. Отчёт: вердикт первым, потом авторские добавки как решения, потом непроверенное.
6. Новый билд от владельца — перепроверка, а не перечитывание: подтверждить правку в мастере
   И в каждой партии, решающая метрика сдвинулась ровно на ожидаемое. README с заявлением
   «исправлено» — заявление, не доказательство.
7. Слой пометок (`<words>`, `<dynamics>`) не виден в питч-дифе — проверять текстом отдельно.
8. Числа из чужого отчёта не наследовать: пересчитать на файле, который держишь в руках,
   и назвать расхождение одной строкой.

## Workflow C: малая правка готового мастера

Согласованный набор правок в присланном мастере — тот же файл с изменениями и ничем больше,
доказуемый дифом. Работать строковой заменой внутри слайса партии, НЕ parse-and-reserialize
(смешанное форматирование: ресериализация переписывает все байты и уничтожает доказательство).
Якорь `<measure number="N">` не уникален — уникален только слайс от `<part id="Pxx">` до
следующего; `count(old) == 1` до каждой замены. Полные рецепты (замена, пересборка `.mxl`,
верификация, кадры до/после) — `references/master-surgery.md`. Добавление инструмента в
MuseScore 4 мастер — `references/mscx-add-part.md` (строковая вставка в `.mscx`, НЕ MusicXML
round-trip: он теряет вёрстку и стиль страницы; геометрия страницы живёт в `score_style.mss`).

## Отчёт: вердикт первым

- **Измерено** (валидатор, рендер, пересчёт), **предположено** (вкусовые решения),
  **неизвестно** (как звучит — только живое прослушивание). Помечать каждое утверждение.
- Вердикт — первой строкой: «такты 155 и 158 неверны, вот доказательство», а не список
  кандидатов «для дальнейшего изучения».
- Механически проверено vs требует ушей — сказано отдельно.

## Правила меди — самое частое

Полные таблицы и лимиты — `references/brief.md` (диапазоны, транспозиции, знаки при ключе,
сурдины, воусинг, выносливость). Выжимка:

- Валторна in F звучит ч.5 ниже написанного, труба Bb — б.2 ниже; тромбон и туба — без
  транспозиции. Знаки при ключе партии: Bb +2 диеза, валторна F +1 диез, Es +3 диеза.
- Секция держится в ~2 октавах; разрыв >октавы между соседними голосами — между низкой
  и верхней медью, не в середине.
- Туба — основной тон; мелодия у тубы = намеренное соло. Валторны держат середину.
- Выносливость (любитель): трубы ≤4 тактов mf, ≤2 тактов ff вверху подряд; вдох каждые
  2–4 такта; «высоко и тихо» — не писать.
- Сурдины: смена ≥10 секунд (TOR), не внутри быстрой фразы; stopped horn (`+`) звучит
  ~полутон выше написанного и меняет высоту, сурдина — только тембр.

## Питфоллы

- `validate_brass.py` матчит инструменты по подстроке: alto trombone меряется по строке
  тенорового (E2–Bb4) — читать как предупреждения регистра; подлинно высокие ноты
  тубы/источника проверять по тактам, прежде чем предлагать правку.
- С Percussion-становыми валидатор всегда даёт REJECT («has no notes») — ударные для него
  `<unpitched>`; читать `!`-строки, вердикт-линию дефектом сдачи не считать.
- Скрытые паузы (`print-object="no"`) и паузы без `<type>` — классифицировать, прежде чем
  называть дефектом: босые целотактовые паузы MuseScore печатает правильно, это не ошибка.
- Темп: печатный `<metronome>` и `<sound tempo>` могут расходиться — цитировать оба с ярлыками.
- Не называть пробные скрипты именами stdlib-модулей (`json.py`, `inspect.py`) в рабочем
  каталоге — импорт перехватывается.
- Первый пункт чек-листа сдачи: `references/brief.md` §8 — прогонять целиком перед сдачей.

```bash
PY="$LOCALAPPDATA/Programs/Python/Python312/python.exe"
"$PY" scripts/validate_brass.py --write-demo demo.musicxml
"$PY" scripts/validate_brass.py demo.musicxml --level amateur
```
Демо-фикстура обязана дать ровно **2 жёсткие ошибки** (труба D6 выше C6, туба C1 ниже D1,
оба в такте 4) и **9 предупреждений**. Числа съехали — валидатор регрессировал.
